# Promo Finder — Design

Date: 2026-11-05 · Status: draft for approval · Problem: Kuku AI Generalist Assignment, Problem 1

## 1. Intent and why

Kuku editors currently watch every episode of every microdrama by hand to pick promo clips (20–60s, posted to TikTok / Reels / Shorts to pull in new viewers). New shows ship weekly, so this does not scale.

Promo Finder is a command-line tool that reads a show's timestamped screenplays and outputs a **ranked shortlist of promo candidates**. For each candidate it gives the episode(s) and exact start/end timestamps of every segment, plus the hook, the cliffhanger and one line on why it works. It also reports where it is likely picking badly.

An editor still makes the final call. The tool turns "watch 50 episodes" into "review the top 15 suggestions".

Who it is for:
- **Now:** Kuku's reviewers, who read the repo, the raw outputs and the 2-page doc, then watch it run on a **new show** in the interview, possibly with a stronger model behind it.
- **Imagined user:** a Kuku promo editor.

## 2. Goals, non-goals, anti-goals

**Goals**
- Find promos across all episodes: single continuous clips (the main case) and multi-segment promos joined from one or several episodes.
- Every promo satisfies the brief's three tests: a hook in the first 3 seconds, a cliffhanger at the end, and it makes sense to a stranger.
- Timestamps are **exact and trustworthy**. They are copied from the screenplay by code and never generated by the model.
- Rank promos and explain the ranking ("post these first because …").
- Run again on any new show folder with one command. Swap the model by editing config, not code.
- Produce honest quality evidence: automatic checks, a small hand-labelled comparison and a categorised list of failures.

**Non-goals**
- No video editing, music, captions or overlays.
- No UI or deployed app. It is a GitHub repo with a CLI.
- No reading of actual video. The screenplay is the only input.
- No training or fine-tuning.

**Anti-goals (it fails even if it "works" when…)**
- Timestamps cut mid-line or land on moments that don't exist.
- The top 10 are near-duplicates of the same scene.
- Promos need show knowledge to follow, e.g. they open on an unexplained name.
- A promo includes its own resolution, so the cliffhanger is already answered inside the clip.
- It only runs on this show's quirks, so the new show in the interview breaks it.

## 3. Constraints

- **Time:** about 2–3 hours of build. Scope cuts are listed in §11.
- **Cost:** free tier only. Models come from NVIDIA's API catalogue (build.nvidia.com). It is OpenAI-compatible at `https://integrate.api.nvidia.com/v1`, credit-based and rate-limited, roughly 40 requests/min (verify on sign-up).
- **Confidentiality:** the input pack is Kuku's content. It must **never be committed** to the repo. See §10 for outputs, which quote dialogue.
- **Swappable model:** every LLM call goes through one client built from config: base URL, API key environment variable and model name per stage.

## 4. What the input looks like (measured on the pack)

- 50 `.txt` files, one per episode (`episode-NNN-Episode <id>.txt`), about 530 KB / ~130k tokens in total.
- Episode length is 70–200 s (average ~123 s), with 1–5 scenes and 37–121 timed blocks per episode.
- Header: `EPISODE NUMBER`, `EPISODE LOGLINE` (one-sentence summary) and `CONTINUITY NOTES`.
- Body: `SCENE NN`, then `Scene heading / Scene start / Scene end`, then blocks:
  ```
  **MATRIARCH (Blunt, Unforgiving):**
  Start: (00:18.00) | End: (00:19.40)
  "Not anymore."
  ```
  Block types counted: CAMERA 1754, DIALOGUE 1487 (speaker + emotion tag in parentheses), ACTION 372, SOUND FX 114.
- Timestamps are `MM:SS.ss` and **relative to each episode**.
- **Quirk:** Episode 6 uses upper-case scene headers (`SCENE HEADING:`). The parser must be case-insensitive and tolerant.
- **Signal:** writers sometimes flag beats directly ("swells to an ominous cliffhanger peak" in 22 episodes, "gasp" in 28, "Cut to black" in 4). But "slap" appears in only 1 episode, so keywords alone are weak.
- CAMERA blocks tile the timeline end-to-end. **Shot boundaries are the natural, clean cut points.**

## 5. Approaches considered

| | Approach | Trade-off |
|---|---|---|
| A | LLM reads each episode and returns promos with timestamps | Fastest to build, but hallucinated or blurred timestamps, mid-line cuts, unstable scores, and failures that are hard to explain |
| **B** | **Code handles structure, the LLM handles judgement (chosen)** | Exact timestamps, inspectable stages and a per-stage model swap. Costs more moving parts and ~2–3 h to build |
| C | Rules and keywords pick, the LLM only writes explanations | Cheap and deterministic, but misses quiet but devastating lines ("Not anymore.") and doesn't generalise to a new show's writing style |

**Chosen: B.** It is the only option where timestamps are correct by construction. Its split (code parses and assembles, the AI judges drama, a human approves) maps directly onto the grading lens "what you gave to AI, what you kept as code, where a human stays in the loop". C's rules survive inside B as cheap extra signals.

## 6. Architecture

```
 show folder (*.txt)
        │
 [1] PARSE (code) ───────────► beats.jsonl, episodes.json
        │
 [2] RULE SIGNALS (code) ────► per-beat features
        │
 [3] SHOW BIBLE (LLM, 1 call) ► bible.json  (premise, characters → plain roles, arc per episode range)
        │
 [4] BEAT TAGGING (LLM, 1 call/episode × N votes) ► tags/ep_NNN.json  (hook & cliffhanger beats, by ID + quote check)
        │
 [5] WINDOW BUILDER (code) ──► candidates.json  (single-segment, 20–60 s, snapped to shots, scored, deduped)
        │
 [6] STITCHER (LLM proposes, code validates) ► multi-segment candidates
        │
 [7] JUDGE (LLM, top ~30) ───► blind standalone score, first-3-seconds test, hook/cliffhanger text, why-it-works
        │
 [8] CUT REFINEMENT (code offers options, LLM picks) ► best start/end per finalist
        │
 [9] PAIRWISE RANKING (LLM, top 15) ► "which would you post first?" tournament → final order
        │
[10] REPORT (code) ──────────► promos.json, promos.csv (with editor ✓/✗ column), report.md, run_meta.json
        │
[11] FEEDBACK (code, next run) ◄ editor-marked promos.csv → few-shot examples + weight tweaks

 Side commands:  eval (score against hand-picked set) · --dry-run (estimate calls/tokens) · resume from any stage
```

Every stage reads the previous stage's files from `outputs/<show-slug>/` and writes its own. Any stage can be re-run alone, results are cached, and every intermediate file doubles as the "raw outputs" deliverable.

### Stage 1 — Parse (code, no AI)
- Reads every `*.txt` in the folder and sorts them by `EPISODE NUMBER` (falling back to the filename number).
- Produces one **Beat** per timed block: `{ep, beat_id (e.g. "E01-B014"), idx, scene, type: CAMERA|ACTION|DIALOGUE|SFX, speaker, emotion_tags[], text, start_s, end_s}`.
- Produces one **Episode** record: `{ep, logline, continuity_notes, duration_s, scenes[]}`.
- Case-insensitive and whitespace-tolerant. Unknown block headers are kept as type `OTHER` with a warning, never dropped silently.
- Validates that start ≤ end and that times stay inside the scene range, then logs anomalies to `parse_warnings.txt`.
- **Swappable input reader (robustness #9).** Parsing goes through a small reader interface, `read_show(path) -> list[Episode]`. The default reader handles this pack's format. A show in a different format needs only a new reader module (selected with `--reader`), and nothing downstream changes.
- **Fail loudly.** A parse health summary is printed and saved: episodes found, lines per episode, lines with no timestamp, and times out of order. If more than 5% of lines in any episode fail to parse, the run **stops** with that report instead of continuing on bad data (override with `--force`).

### Stage 2 — Rule signals (code)
Computes cheap per-beat features, used as score boosts and as hints in the LLM prompt:
- **Keyword hits:** slap, strike, gasp, reveal, kneel, kiss, blood, "pregnant", "divorce", "dead", "who are you", "cliffhanger", "cut to black", "freeze".
- **Emotion tags** on dialogue, e.g. Furious, Shocked, Trembling, Cold, Commanding, scored by a small intensity lexicon.
- **SOUND FX** swell / sting / silence cues.
- **Position:** within the last 10 s of the episode, at a scene boundary, or a question/exclamation line.
- **Density:** dialogue lines per 10 s, since fast exchanges suggest confrontation.

The lexicon lives in `config/signals.yaml` so it can be tuned per show.

### Stage 3 — Show bible: full-show story context (LLM, 1 call)
Before any episode is tagged, the model gets the **whole story arc, including what happens later**. That lets it judge each moment knowing where the story goes.
- **Input:** all 50 loglines and continuity notes (~4k tokens). These are the writers' own summaries, so the model compresses the story without inventing it.
- **Output (JSON):**
  - `premise`: 2 lines
  - `characters`: name → plain role a stranger understands ("Mara — jilted bride, the heroine"; "Lena — her cruel sister")
  - `arc`: the story in 6–10 acts, each with its episode range
  - `episode_summaries`: one line per episode
  - `major_reveals`: each twist with the episode where it lands and the earlier episodes that set it up
- **Context given per episode in Stage 4, in two layers:**
  - *global*: premise, characters, arc and major reveals
  - *local*: the summaries of the previous and next episodes, plus the current episode's logline

  The local layer is what lets the model see that a cliffhanger is answered in the first seconds of the next episode.
- **Used by:** Stage 4 (story importance, where each cliffhanger resolves, spoiler flags), Stage 6 (cross-episode joins need the whole arc) and Stage 10 (spoiler-aware ranking and per-act diversity). It is **not** given to the Stage 7 judge (see below).

### Stage 4 — Beat tagging (LLM, 1 call per episode, the core AI step)
- **Input:** the bible context, the episode logline and a compact numbered transcript. DIALOGUE, ACTION and SFX are always kept.
- **Visual moments (robustness #8).** Slaps and reveals are often written only in ACTION or CAMERA lines. CAMERA lines are kept when they contain strong visual verbs or framing words (slap, strike, grab, collapse, kneel, kiss, tears, reveal, close-up on, push-in, freeze, smash), using the list in `config/signals.yaml`. Other CAMERA lines are dropped to save tokens. Example of a compact line:
  `[14] 00:18.0–00:19.4 DIALOGUE Matriarch (Blunt): "Not anymore."  {sig: question-reply, cold}`
- **Asks for strict JSON:**
  - `hooks`: `[{beat_id, hook_score 1–10, story_importance 1–10, kind: slap|reveal|shocking_line|threat|humiliation|romance|danger|other, why}]`. A hook is something that stops a scroller **in its first 3 seconds with no context**.
  - `cliffhangers`: `[{beat_id, cliff_score 1–10, story_importance 1–10, open_question, resolved_by: beat_id | "next_episode" | "later_episode:N" | null, spoiler_level: none|minor|major}]`. A `resolved_by` beat inside the same episode tells the builder where the clip **must** end before.
  - `context_beats`: beats that explain who/what, used to judge standalone-ness.
- **Guarding against hindsight bias.** Because the tagger knows the ending, it will tend to overrate moments that matter to the plot but mean nothing to a stranger. Three guards:
  - The two scores are kept **separate**. The prompt says to use the show context *only* for `story_importance`, `resolved_by` and `spoiler_level`, and to score `hook_score` / `cliff_score` "as a stranger who has never seen the show".
  - `story_importance` gets only a small weight in ranking.
  - The Stage 7 judge is blind, which catches anything that only works with context.
- **Scoring examples (robustness #5).** The prompt includes 3–4 short anchor examples written for this tool, not Kuku text, showing what a 3/10, 6/10 and 9/10 hook and cliffhanger look like. That keeps a "7" meaning the same thing on every show. Approved promos from editor feedback (Stage 11) are added as extra examples on later runs.
- **Quote check (robustness #1).** For every tagged beat, the model must also return `quote`: the first ~6 words of that line. Code compares it with the real beat text using a normalised fuzzy match (ratio ≥ 0.8). A mismatch means the model cited the wrong line, so the tag is **discarded** and counted in `run_meta.json` as `quote_mismatches`.
- **Validation (code):** the output must parse against a pydantic schema, and every `beat_id` must exist in that episode. Unknown IDs are dropped and logged. On a bad response the call is retried once with the error shown, then the episode is skipped with a warning.
- **Majority vote (robustness #3, on if credits allow).** Each episode is tagged `votes` times (default 3, set in `config/models.yaml`), either at temperature ~0.7 or across 2 different models. A beat is kept only if a majority of runs tagged it (2 of 3), and its scores are averaged. `votes: 1` turns this off for cheap runs. Agreement rates are reported as a stability measure.
- **Why IDs only:** the model never types a timestamp, so it cannot invent one.

### Stage 5 — Window builder (code)
For each hook H (score ≥ `hook_min`, default 6) and each later cliffhanger C in the same episode:
- **Snap the start** to the start of the CAMERA shot containing `H.start`, only if that is ≤ 3.0 s before `H.start`. Otherwise start at `H.start`. This guarantees the hook lands in the first 3 s.
- **Snap the end** to the end of the CAMERA shot containing `C.end`. That shot must not overlap the start of `C.resolved_by` or of any dialogue line after C.
- **Keep** only windows whose duration is in [20, 60] s.
- **Score:** `w_h·hook + w_c·cliff + w_r·rule_signals + w_len·length_fit − penalties`.
  - `length_fit` peaks at 30–45 s.
  - Penalties apply for: a cut inside a dialogue line, a window crossing a scene boundary into a different location without the hook/cliff spanning it, or >40% of the runtime being dialogue-free CAMERA.
  - Weights live in `config/scoring.yaml`.
- **Dedupe** with non-max suppression: if two windows overlap by more than 50%, keep the higher score. Keep at most `k_per_episode` (default 3).
- **Episode-end rule:** an episode's final beat is a natural cliffhanger candidate. Its resolution is in the next episode, so it is safe.

### Stage 6 — Stitcher (multi-segment, LLM proposes, code validates)
This is a small, explicitly experimental stage.
- **Shortlist:** the top ~20 hooks and top ~20 cliffhangers across the show, with their text and episode.
- **LLM step:** given the bible, the model proposes up to 8 combinations of 2–3 segments that tell a mini-story, in viewing order. Each segment is a hook or cliffhanger beat ID plus how much surrounding context to include.
- **Code checks** for every combination:
  - each segment is built with the Stage 5 snapping rules and is ≥ 5 s
  - the total length is 20–60 s
  - segments stay in chronological order
  - the first segment opens on a hook and the last ends on a cliffhanger

  Invalid combinations are dropped and logged.

### Stage 7 — Judge (LLM, top ~30 candidates)
- **Stranger test:** the judge sees **only the clip's text**, not the bible, and is asked:
  - Who is this about, and what's at stake?
  - What question does it leave open?
  - Is anything confusing to a new viewer?

  It returns `standalone 1–10` and `confusing_bits[]`.
- **Copy:** it writes the `hook` (what happens in the first 3 s), the `cliffhanger` (the open question) and `why_it_works` (one line).
- **Flags:** `spoiler_risk` (reveals a twist from late in the show) and `resolution_leak` (the clip answers its own question).
- The judge model is set separately in config, so a stronger model can be pointed at this stage alone.

- **First-3-seconds test (robustness #7).** This is a separate tiny call per candidate. The model sees **only the text of the first 3.0 s** of the clip and answers: "Scrolling past, would this make you stop? 1–10, and what grabbed you." It tests the hook rule directly. A candidate scoring below `hook3s_min` (default 5) is demoted.

### Stage 8 — Cut-point refinement (code offers, LLM picks; robustness #6)
For each finalist (top ~15 after judging):
- **Code generates options:** up to 6 alternative cuts by moving the start one or two CAMERA shots earlier or later and the end one or two shots earlier or later. Each option is checked against every Stage 5 rule: 20–60 s, hook within 3 s, no mid-line cut, no resolution beat inside.
- **The LLM picks** one option by letter (A–F) given the text of each and says why, e.g. "B opens on the slap itself; A wastes 2 s on a wide shot".
- If the pick is invalid or missing, the original cut is kept. Timestamps still only ever come from code.

### Stage 9 — Pairwise ranking (LLM; robustness #4)
Absolute 1–10 scores are poorly calibrated, so the **final order of the top 15** comes from head-to-head comparisons:
- About 4 Swiss-style rounds pair promos with similar running records. For each pair the judge sees both clips' text, with the order shuffled to cancel position bias, and answers "Which would you post first to pull in new viewers, and why?"
- The results produce an Elo-style rating, which sets the final order of the top 15. The "why" sentences from the wins become the "post first because" notes in the report.
- Candidates below the top 15 keep the score-based order from below.

### Stage 10 — Rank and report (code)
Score used to choose the top 15 that go into Stages 8–9: `final = 0.30·hook + 0.30·cliff + 0.25·standalone + 0.05·story_importance + 0.10·rules − flags` (a `spoiler_level: major` flag demotes but does not remove a promo), then diversity re-ranking: no more than 2 of the top 10 from the same scene, and no more than 3 from the same story act in the Stage 3 `arc`. The **final order of the top 15 is the Stage 9 pairwise result**. Everything below the top 15 is ordered by `final`.

Assumption for "post first": acquisition promos send viewers to **Episode 1**. So among similar scores, prefer promos from early episodes (≤ 10). They set up the premise the viewer will land on and spoil less. This is configurable.

Outputs in `outputs/<show-slug>/`:
- `promos.json` (full detail)
- `promos.csv`, one row per promo, with segments as `E03 00:41.20–01:12.80; E07 …`, plus empty `editor_verdict` (✓/✗) and `editor_note` columns for Stage 11
- `report.md`, a human-readable ranked list giving, for each promo: segments, length, hook, cliffhanger, why it works, scores and a "post first because" note for the top 5, plus the invariant-check results and parse health summary
- `run_meta.json`: the model that actually answered each call (including fallbacks), prompt versions, timings, call count, token usage, quote mismatches, vote agreement and warnings

### Stage 11 — Editor feedback loop (code; robustness #12)
- **What the editor does:** marks `editor_verdict` ✓ or ✗ in `promos.csv`, with an optional one-line note ("too talky", "needs context", "great slap").
- **What the next run does** with `--feedback <path to marked promos.csv>`:
  1. **Few-shot examples.** Up to 4 ✓ promos and 2 ✗ promos, with their notes, are added to the tagger and judge prompts as "the editor liked / rejected these". For a new show, feedback from earlier shows is used.
  2. **Weight nudges.** A simple, transparent rule: for each scoring component, compare its average among ✓ and ✗ promos and shift its weight by up to ±0.05. The result is written to `config/scoring.learned.yaml`, which the user can inspect and revert. No training is involved.
  3. **Growing gold set.** ✓ promos are appended to the eval set (`eval/gold.yaml`, episode and timestamps only, no script text), so `eval` measures against real editor choices over time.
- With fewer than 10 marked promos, only step 1 applies. The weights stay put to avoid over-fitting to a handful of opinions.

## 7. Model access and swapping

- `config/models.yaml` defines `base_url`, `api_key_env` (default `NVIDIA_API_KEY`) and, for each stage (`bible`, `tagger`, `stitcher`, `judge`, `hook3s`, `refine`, `pairwise`), an **ordered list of models**.
- **Fallback chain (robustness #2).** If a model returns repeated 429/5xx after retries, invalid JSON twice, or a "model not found" error, the client moves to the next model in that stage's list. An example chain is Nemotron, then `meta/llama-3.3-70b-instruct`, then a small fast model. Every call records which model actually answered.
- Default picks are a Nemotron instruct model (e.g. `nvidia/llama-3.3-nemotron-super-49b-v1`) for the tagger and judge, plus a cheaper or faster model optionally used for the bible and stitcher. Model IDs are verified against the live catalogue at build time.
- There is one `LLMClient` wrapper (OpenAI SDK). It provides JSON mode where supported, otherwise "extract the first JSON object". It also handles retry with exponential backoff on 429/5xx, a request-rate limiter, an on-disk cache keyed by `hash(model + prompt + vote_index)` and token accounting. The vote index is included so that majority-vote runs don't just return the same cached answer three times.
- Any OpenAI-compatible endpoint (Kuku's own API, Groq, Ollama) works through config alone. CLI flags override config, e.g. `--model judge=...`.
- Prompts live as versioned text files in `prompts/` so they are visible and editable.
- **Resume and dry run (robustness #10).** Each stage writes its output file and skips work whose output already exists, unless `--fresh` is passed. Per-episode tagging saves after every episode, so a crash at Episode 37 resumes at 37. `--dry-run` parses the show and prints the planned number of calls and estimated tokens per stage without calling any model.

## 8. Quality checking

1. **Automatic invariants** on every run, reported in `report.md`:
   - duration is 20–60 s
   - the hook beat starts ≤ 3 s into the clip
   - no cut lands inside a dialogue line
   - no resolution beat falls inside the clip
   - every timestamp maps back to a real block
2. **Hand-labelled comparison via `python -m promofinder eval` (robustness #11).** Before looking at tool output, pick by hand ~12 promo moments from ~8 episodes spread across the show (early, middle, late), as an editor would. Store only the episode and timestamps in `eval/gold.yaml`. The `eval` command prints:
   - recall@20: how many hand-picked moments appear in the top 20 with ≥ 50% time overlap
   - precision@10: from the editor verdicts in `promos.csv`, how many of the top 10 you would actually post
   - invariant pass rate
   - quote-mismatch rate

   It saves `eval_<timestamp>.json` so every prompt or model change is measured against the last run.
3. **Stability:** report the majority-vote agreement rate from Stage 4 and the top-10 overlap between two full runs.
4. **Model comparison (optional, if credits allow):** compare the tagger and judge on Nemotron against another free model and note the differences.
5. **Failure log:** review the top 20 by hand and categorise every bad pick. Expected categories:
   - visual-only hooks the text undersells (a slap described only in CAMERA)
   - context-dependent cliffhangers
   - unexplained names
   - the clip resolves itself
   - too talky
   - near-duplicates

   This feeds the "where does it pick badly" section.

## 9. Scale and cost (for the doc)

- **Per show, with every feature on:**

  | Stage | Calls |
  |---|---|
  | Bible | 1 |
  | Tagging (3 votes) | 150 |
  | Stitcher | ~1 |
  | Judge | ~30 |
  | First-3-seconds test | ~30 |
  | Cut refinement | ~15 |
  | Pairwise ranking (~4 rounds × 7–8 pairs) | ~30 |
  | **Total** | **≈ 260 calls, ~700k–900k tokens** |

  With `votes: 1` it drops to ≈ 160 calls. At ~40 requests/min that is roughly 5–10 minutes. NVIDIA's free credit allowance must be checked at sign-up, so run `--dry-run` first, and use `votes: 1` while developing so credits go to the final run.
- **Cost at Kuku volume:** at typical paid open-model prices this is cents per show.
- **Throughput:** runtime is bound by the rate limit, not compute. Episodes are tagged in parallel up to the limit, and the cache makes re-runs nearly free.
- **Human in the loop:** an editor reviews `report.md` and marks ✓/✗ in `promos.csv`. Stage 11 feeds those marks back as prompt examples, weight nudges and a growing gold set. The editor's job shrinks from watching 50 episodes to judging about 15 suggestions.

**Publishing (decided with the user):** the public GitHub repo holds **code only**. `outputs/` is git-ignored. Everything the tool generates goes in an anyone-with-link Google Drive folder that is submitted as the "raw outputs" link: `beats.jsonl`, tags, candidates, `promos.json/csv`, `report.md` and `run_meta.json`. These quote Kuku's screenplay. The README explains how to reproduce them. Test fixtures are synthetic, never Kuku text.

## 11. Scope cuts if time runs short (in order)

With all twelve robustness features, this is realistically **5–7 hours** of build, more than the brief's suggested 2–3 hours. That is a deliberate choice by the user. To stay safe, build in this order so a working tool exists at every point:

| Milestone | What's in it | Rough time |
|---|---|---|
| **M1: core, a submittable result** | Stages 1, 2, 4, 5, 7 and 10; quote check (#1); fallback chain (#2); visual lines kept (#8); reader interface and fail-loud checks (#9); resume and dry run (#10); invariant checks | ~2.5 h |
| **M2: better judgement** | Stage 3 bible with two-layer context; scoring examples (#5); first-3-seconds test (#7); `eval` command (#11) and hand-labelled set; Experiments A and B (§13.2) | ~1.5–2 h |
| **M3: better ranking and cuts** | Pairwise ranking (#4, Stage 9); cut refinement (#6, Stage 8) | ~1 h |
| **M4: extras** | Majority vote (#3); stitcher (Stage 6); editor feedback loop (#12, Stage 11) | ~1–1.5 h |

If time runs out, ship the last completed milestone and list the rest as "designed, not built" in the solution doc. The honest partial is what the brief asks for.

## 12. Decided vs. left to the builder

**Decided with the user:**
- Problem 1
- NVIDIA API catalogue models (Nemotron preferred)
- a GitHub repo with a CLI and no deployed app
- approach B
- the full-show summary given to the tagger (the user's idea), with hindsight-bias guards
- all twelve robustness features (#1–#12)

## 13. "Which AI tools, and where they got it wrong" (mandatory for the solution doc)

The brief requires naming the AI tools used and **one place they got it wrong**. The design makes sure there is a **real, documented** failure to report, ideally one that justifies a piece of the architecture. Failures must be **observed, never written in advance**, because the interview will probe them.

### 13.1 Dev log (kept throughout the build)
`docs/ai-log.md` is committed and contains no Kuku script text. It has one entry per notable AI mistake:

| Field | Content |
|---|---|
| Tool | e.g. Claude Code, Nemotron-49B via NVIDIA API |
| What I asked | one line |
| What it did wrong | one line plus a pointer to the saved raw output (stored in the Drive folder if it quotes the script) |
| How I caught it | test, invariant check, eval, or reading the output |
| What I changed | the fix, and which part of the architecture it justifies |

**Already logged (real, from the design session with Claude Code):**
1. **Missed Episode 6.** The first data-scan script matched only `Scene end:` and reported 49 episodes, because Episode 6 uses `SCENE END:`. It was caught because the count didn't match the 50 files. Fix: a case-insensitive parser, the parse health summary and the fail-loud threshold (§6 Stage 1, #9), plus a parser test for the upper-case variant.
2. **Cache would have broken voting.** The first cache design keyed calls by `model + prompt`, so the 3 majority-vote runs would have returned one cached answer three times, faking "agreement". It was caught on review of the design. Fix: the vote index was added to the cache key (§7).

### 13.2 Two planned experiments that test the architecture's main claims
These are cheap, about 10 calls each, and run during M1/M2. Whatever they show, good or bad, is reported honestly.

**Experiment A: "Does the LLM get timestamps wrong if we let it write them?" (justifies approach B)**
- On 5 episodes, run a naive Plan-A prompt: "Here is the screenplay; return promo clips with start/end timestamps."
- Code checks every returned timestamp against the real blocks and counts:
  - timestamps that don't match any block boundary
  - cuts inside a dialogue line
  - clips outside 20–60 s
  - times beyond the episode length
- Save the raw responses as `eval/exp_a_plan_a_raw/` (in Drive) and the counts in `eval/exp_a_summary.json`.
- If it does fail, this is the headline "where AI got it wrong", and it justifies line IDs only, the quote check and code-built windows. If it doesn't, report that too, and argue for B on consistency and the cut-on-shot-boundary rule.

**Experiment B: "Does the full-show summary cause hindsight bias?" (justifies the separate scores and the blind judge)**
- On 8 episodes, tag twice: once **with** the Stage 3 show context and once **without**.
- For beats whose `hook_score`/`cliff_score` rise by 2 or more points with context, check whether the blind Stage 7 judge rates the resulting clips low on `standalone`. That pattern means "the tagger overrated a moment because it knew the plot".
- Save the side-by-side comparison as `eval/exp_b_hindsight.json`.
- Pick the clearest real example (episode, line, the two scores, the judge's verdict) for the doc.

## 14. Assumptions (to restate in the solution doc)

- Screenplay timestamps match the final video timeline.
- Promos send viewers to Episode 1, so early-episode promos rank higher among near-ties.
- A "hook in the first 3 s" can be judged from text, and visual-only moments are a known weak spot.
- Multi-segment promos are a secondary format. Most real promos are one continuous stretch, as the brief says.
- Spoilers of late-show twists are acceptable but are flagged, not hidden.
